LangGraph deep dive

What happens between "Twilio sends a message" and "the call is cut": how the session is created and kept, what the graph's nodes read and write, where each piece of information comes from, and every way a call can end. Real values come from call 19, the 11:23 medicine reminder.

Three ideas to hold on to. (1) A session is a Python object, CallSession, that lives in the server's memory for the length of one call. (2) The graph is a set of small functions (nodes) that LangGraph runs in an order that depends on the data. (3) The state is one dictionary that every node can read and add to; the conversation memory is one key inside it.

STEP 1How the session is created and stored

Nothing about the conversation exists until the parent answers. Then Twilio asks our server what to say, and that request creates everything. The picture shows the whole path, including what happens when something is missing.

STEP 2What happens when there is no session

A session can be missing if the server restarted during the call (the dictionary lives in the process, so a restart empties it), or if a turn request arrives for a call this process never started.

  1. GatherCalls.turn finds self.sessions.get(call_id) is None and logs "no session for this turn".
  2. It answers Twilio at once with: "I am sorry, we got disconnected. I will call you again shortly. Goodbye." followed by a hang-up. The parent hears that, then the call ends.
  3. It calls _abandon_orphan(call_id), which runs in a worker thread: it moves the call to abandoned (reason "the server lost this conversation"), writes a call.orphaned audit event, and runs the outcome engine straight away. With no conversation to read, the engine decides on the call's status and schedules a retry.
  4. Twilio then sends its "completed" status. The status handler sees the call is being handled and leaves it alone.
  5. When the background work ends, the call is removed from the "finishing" set, so nothing is left behind.
Fixed (this was a gap). Before, nothing was recorded at that point, the status handler skipped the call, and it stayed in_progress until the reaper failed it up to 25 minutes later. Now it is recorded and retried at once. There is a test for it (test_gather_turn_with_no_session_records_the_call_as_abandoned_at_once). Not recorded: the earlier part of that conversation, because the memory of it was lost with the session.

Other "missing" cases: if the agent is too slow six times in a row the call ends politely (a session still exists, so it is recorded). If a Twilio status arrives for a call that never opened a session, the status handler records it normally (no answer, failed).

STEP 3The graph: nodes, edges and decisions

A LangGraph graph is a set of functions (nodes) plus rules (edges) that say which node runs next. Some edges are fixed; the rest are small router functions that look at the state and return the name of the next node. graph.invoke(input, config) runs from START until it reaches END, then returns the final state.

The routers (the decisions)

RouterRuns afterRule
route_startSTARTstate.started true means a later turn, go to safety. False means the first turn, go to open.
after_safetysafetyEmergency words found: escalate. Three silences in a row: give_up. Otherwise: agent.
after_agentagentThe model asked for actions (pending not empty): tools. Otherwise: finish.
after_toolstoolsagain true (a result matters or a tool failed, and fewer than 4 steps so far): back to agent. Otherwise: finish.

The loop agent, tools, agent is the "agent loop": the model proposes, code executes, the model sees the result and speaks. open, escalate, give_up and finish all go straight to END.

STEP 4The state: the one dictionary every node shares

Each node receives the whole state and returns only the keys it wants to change. LangGraph merges that into the state (a returned key replaces the old value). The state is saved by MemorySaver after every node, under this session's thread_id, and loaded again at the start of the next invoke. That is how the conversation survives from one sentence to the next.

Memory lives inside the session object. Because every CallSession builds its own graph with its own MemorySaver, the conversation exists only while that object does. There is no copy in the database (the transcript rows are a log, not the memory). That is why "no session" means the agent no longer remembers anything.

What finish does to the reply

  1. If the model errored and said nothing: "I am sorry, I did not catch that. Could you say that again?"
  2. If nothing was said and the call is not ending: "Sorry, could you say that again?"
  3. If 24 parent turns have happened: a polite goodbye and end the call.
  4. If the exact same line has now been said three times: a polite goodbye and end the call.
  5. Cut the reply to 60 words; if it looks like it leaks an instruction, a phone number or an e-mail, replace it with "I can only help with your check-in."
  6. Reply = stalling lines + the final line. End reason: emergency if an emergency alert was raised, callback if a booking succeeded, otherwise completed.

FOUND WHILE TRACING, AND FIXEDProblems this walk-through turned up

1. A call-back opened with a stale line. Fixed. On a call-back, open_ used to ask the model to continue from the earlier transcript and used its reply as the opening question. That transcript ended with "I will call you again at eleven thirty-six", so the model repeated it at the start of the call-back (call 21), and the call then drifted to a question about food. Now only a call that was cut off mid-conversation is continued by the model. A call-back, or a retry after no answer, uses the scripted opening (the routine's own question), and the old transcript is no longer put in the prompt for those. Checked with the real model: the call-back opened with "It is time for your Metformin 500mg... Have you taken it?", and a silence was answered with a medicine question, not a food one. Two tests cover it. I did not see the food question reproduce after the fix, but I never found its cause either, so I cannot promise it is gone.
2. A call with no session was not recorded for up to 25 minutes. Fixed (see section 2).
3. The "finishing" set in gather.py grew forever. Fixed. A call is now removed from it when its background finish is done.
4. Still open: confidence is stored but unused. Twilio's score for each phrase is saved with the transcript row; nothing decides on it yet.
