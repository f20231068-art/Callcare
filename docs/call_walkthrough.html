Anatomy of a Call

A real lunch check-in with the live model: every message the model saw, every JSON it returned, and what the code did in between.

  • 2 parent turns
  • 4 model calls

What the model returns

Always one JSON object with three fields. Nothing happens because the model wrote it; the code reads each field and decides.

sayThe words to speak, or null. Capped, filtered, then sent to text-to-speech.
actionsTools it wants run on this step only, with arguments. Often empty. Each is validated before anything runs.
end_callTrue only on the goodbye. The call closes after the words are spoken.

The small bar on each card is the model's memory: each cell is one message, teal for the parent (and tool results), violet for the model, the newest outlined.

After the hang-up

  1. Close the books. CallSession.finish() writes a call.finished event (steps reached, whether the parent was speaking when the line closed) and marks the call completed.
  2. Summarise. The post-call pipeline writes the caregiver's summary and sends the notification.
  3. Decide what's next. On a real phone call the outcome engine sees the call-back already booked during the call, records followup.already_scheduled and adds nothing. This capture ran on the evaluation channel, so that step did not run.

What to take from it

  1. The model proposes; a fact or a booking becomes real only when a tool succeeds. Words written before a result-matters tool has run are thrown away.
  2. A refusal is just another message. The model reads it, explains it, and offers something that works.
  3. Each call is sent the whole conversation so far, so the model always has the full context, and the prompt grows a little each step.
  4. A call of about a minute is only a handful of model calls. The model's share is a few seconds; the rest is speech and the parent's pauses.
