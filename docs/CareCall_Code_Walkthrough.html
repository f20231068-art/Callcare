CareCall code walkthrough

Eight files do most of the work. This page explains what each one holds, when it runs, what technology it uses, and how it helps the app, then follows real users through the app and shows which function in which file runs at each step.

THE BIG PICTUREHow the eight files connect

Think of layers. A request arrives at api.py (not one of the eight; it is the doorway). It hands work to one of four files that deal with the outside world: accounts and onboarding for the caregiver's browser, gather or bridge for a phone call. Both phone files hand the conversation to session, which runs the converse graph and, when the call ends, post_call. Every file that stores or reads anything goes through db.

Arrows point from the caller to the callee. Files not among the eight (db_tools.py, planner.py, outcome.py, twilio_api.py) appear in the scenarios where they matter.

THE EIGHT FILESWhat each file is, when it runs, and why it matters

accounts.py

109 lines · who is this caregiver?
When it runs
Sign-up, login, logout, and on every request the dashboard makes (to work out whose data to show). Also whenever a phone number is typed anywhere.
What is inside
hash_password / check_password
Salted scrypt hashing and comparison. The password itself is never stored.
normalize_phone
Turns 98765 43210 into +919876543210. Twilio needs international format.
signup
Validates email, password length and name, creates a Caregiver and an Account in one transaction.
login
Checks the password, creates a random token, stores only its SHA-256 in auth_sessions, returns the token for the cookie.
account_for_token
Cookie token in, caregiver identity out (or nothing if expired or unknown). This is what protects every dashboard route.
logout
Deletes the session row.
How it is used
Called by api.py (auth_signup, auth_login, auth_logout, and the _me() helper that guards every /api/* route). onboarding.py borrows normalize_phone and AuthError. It opens database transactions through db.session_scope.
Stack
Python standard library only for the security parts (hashlib.scrypt, hmac.compare_digest, secrets, re), plus SQLAlchemy to read and write. It knows nothing about HTTP; FastAPI is in api.py.
Why it helps the app
Keeps each caregiver's parents private, keeps passwords safe even if the database leaks, and makes sure every phone number is dialable.

onboarding.py

213 lines · turn a form into a schedule, and the dashboard data
When it runs
When a caregiver adds a parent, creates a one-off reminder, pauses or resumes calls, and every 2 seconds while the dashboard is open.
What is inside
onboard_parent
Validates everything, then in one transaction creates the parent, the caregiver link, meal times (marked as caregiver-set, so the schedule obeys them), medicines and routines. Then plans today's calls.
add_reminder
Creates a Reminder, a routine for it, and a scheduled call at the exact time (seconds included).
set_calling
Turns calling on or off for a parent; off also cancels every waiting call.
snapshot
Builds the whole dashboard in one read: routines with next call, the calendar, the live call and transcript, logged facts, call-backs and recent events.
_owned_parent
The ownership check used by the others: a caregiver can only touch their own parents.
How it is used
Called by the matching routes in api.py. It calls accounts.normalize_phone, planner.plan_day and planner.fire_time (when each routine fires), service.schedule_attempt (insert a call safely), outcome.cancel_pending, tools.add_event (audit trail) and db.session_scope.
Stack
SQLAlchemy queries and joins, zoneinfo and datetime for the parent's local time, regular expressions for validation. Plain functions with no web code, which is why they can be tested without starting a server.
Why it helps the app
It is the bridge between what a person types and what the scheduler needs. Without it there are no routines, so no calls would ever be planned. It also feeds the live view the caregiver watches.

bridge.py

183 lines · live two-way audio (stream mode)
When it runs
Only in live-audio mode (TWILIO_VOICE_MODE=stream, needs a paid Twilio account). One StreamBridge exists for the whole length of each call.
What is inside
run
The receive loop. Reads Twilio's WebSocket messages: start, media (audio, forwarded to Gnani), mark, stop. Always calls _cleanup at the end.
_on_start
Checks the per-call token, creates the CallSession, starts the Gnani speech socket, launches the two background tasks, speaks the opening.
_speak
Text in, audio out: asks Gnani text-to-speech, converts to mu-law frames, sends each to Twilio, then sends a mark.
_pump
Reads Gnani's events. "Speech started" cancels the silence timer and interrupts the agent (barge-in). Final text goes to the inbox.
_consume
Takes each final transcript, runs the agent in a worker thread (session.turn), speaks the reply, ends the call when the agent is done.
_on_mark, _arm_silence, _silence
When Twilio says playback finished, start a 7 s timer; if nothing is said, feed an empty turn so the agent asks "are you still there?".
_cleanup
Stops tasks, closes Gnani, then calls session.finish so the call is always recorded.
How it is used
api.twilio_stream accepts the WebSocket and runs one bridge. The bridge uses the Gnani clients (gnani_speech.py), the audio converters (audio.py) and CallSession.
Stack
asyncio (tasks, a queue, an event), FastAPI's WebSocket object, JSON and base64, audio helpers for mu-law and resampling, asyncio.to_thread to run the blocking agent without freezing audio, and run_coroutine_threadsafe so a worker thread can make the agent say a filler line right away.
Why it helps the app
It is what makes the call feel live: the parent can interrupt, the voice starts within about 0.2 s, and long silences are handled. It keeps all audio details out of the agent.

gather.py

132 lines · turn-by-turn calls (trial mode)
When it runs
In trial mode (TWILIO_VOICE_MODE=gather), which is what your real calls used. Once at the start of a call and once per parent sentence.
What is inside
GatherCalls.start
Creates the CallSession, opens it, and returns the opening as TwiML.
turn
Starts the agent on the parent's words in a worker thread and waits up to 3 s.
_collect / wait
If the agent is slow, tells Twilio "One moment" and to come back to /twilio/wait; repeats up to 6 times.
_answer
Logs what was heard and said; if the agent is done, schedules the finish.
_twiml, _wait_twiml
Builds Twilio's instructions: <Say> the reply inside a <Gather input="speech">, or hang up.
_finish_later / _finish / ended
Run session.finish in the background so the hang-up is instant, and record a hang-up mid-call as abandoned.
_abandon_orphan
If a sentence arrives for a call whose session was lost (a restart), records the call as abandoned and has the outcome engine retry it at once.
How it is used
Called from four routes in api.py: /twilio/voice, /twilio/turn, /twilio/wait and /twilio/status. One shared object CALLS holds the in-memory sessions.
Stack
Twilio's TwiML builder (VoiceResponse, Gather), asyncio (to_thread, create_task, wait_for, shield), and the per-call HMAC token that goes into every URL.
Why it helps the app
Real phone calls work on a free Twilio trial. The same agent, tools and scheduling run behind it, so the scheduler and call-back logic could be tested on a real phone.

session.py

162 lines · one call's conversation, whatever the channel
When it runs
Three times per call: open at the start, turn for every parent sentence, finish at the end. The same in both phone modes and in text tests.
What is inside
CallSession.__init__
Builds the agent for this call: the LLM client and the LangGraph graph from converse.py, a trace id, and the thread id call-<id> that keys the conversation memory.
open
Builds the call context, marks the call in_progress, runs the graph's opening, saves the agent's lines to transcript_turns, returns them.
turn
Saves the parent's words, runs the graph once, saves the reply, returns a TurnResult (lines to speak, done or not, end reason, latency).
finish
Marks the call completed or abandoned, writes call.finished, runs post_call, then outcome.apply to decide the next call.
_save_turn, _span, _user_id
Transcript rows, tracing spans, and the Langfuse user name.
How it is used
Created by gather.start or bridge._on_start. It calls context.build_context, converse's graph, state.transition, post_call.run_post_call and outcome.apply.
Stack
LangGraph (a compiled graph invoked with a config holding the thread id, memory kept by MemorySaver), Langfuse spans through tracing.py, SQLAlchemy, and a dataclass for the result.
Why it helps the app
The phone files only move words in and out; all behaviour lives behind this one interface. That is why the agent can be tested with text and then used on a real phone unchanged.

converse.py

418 lines · the agent: memory, tools, guards
When it runs
Every parent sentence. session.turn runs the graph once per sentence; inside, the model may be called up to 4 times (see the tool loop).
What is inside
system_prompt, task_text
Build the instructions for this call: the three jobs, scope rules, tool list, output format, and the job for this routine.
_llm_step, _normalise
One model call in JSON mode; parses and tidies the reply into {say, actions, end_call}, with one retry if the model did not return JSON.
build_conversation_graph
Defines seven nodes and how they connect: open, safety, escalate, give_up, agent, tools, finish.
open_
The scripted greeting and routine question (no LLM). Only when the previous attempt was cut off mid-conversation does one model call continue it.
safety
Appends the parent's words to memory, checks emergency patterns, counts silences.
agent
One model step; drops commitments (book_callback, add_reminder) if the draft ends with a question.
run_tools
Runs the requested actions through the tool registry, speaks a filler while a slow one runs, feeds results back to the model.
finish
Caps length at 60 words, blocks leaks, stops repeated lines, builds the final reply and end reason.
_trim, _said_before, _hold_for_answer
Keep the last 40 messages, detect a line said three times, hold promises behind a question.
How it is used
Never called directly: session.py builds the graph and invokes it. It calls db_tools.call_tool for every action and db_tools.tools_text to describe the tools to the model.
Stack
LangGraph (StateGraph with conditional edges, MemorySaver), a TypedDict as the shared state, Pydantic for the call context, an HTTPS JSON-mode call to the LLM, regular expressions for the emergency and leak checks, and a Langfuse decorator on each node.
Why it helps the app
It is the part that actually talks to the parent and decides what to do, while code keeps the guarantees (emergency, quote evidence, no unconfirmed bookings).

post_call.py

91 lines · the report after every call
When it runs
Once after every call, from session.finish, whether the call completed, was cut off or failed.
What is inside
run_post_call
Reads everything logged for the call (meals, medicines, acknowledgements, alerts, call-backs), writes a one-line-per-fact summary, finds anomalies (medicine not taken, a meal skipped two days running, an alert), flags calls for review, saves a CallSummary, and creates a Notification for each caregiver.
_meal_line
Formats one meal log as readable text.
How it is used
session.finish calls it inside a Langfuse span. It uses the notifier from notify.py (prints to the console today, or Twilio SMS if switched on). After it, outcome.apply decides the next call.
Stack
SQLAlchemy queries and a few date calculations. No model call; the next-step decision is made by outcome.py.
Why it helps the app
The caregiver gets a readable summary instead of a transcript, and unusual things are highlighted. The summary is also what the outcome engine uses to decide what happens next.

db.py

71 lines · the connection to PostgreSQL
When it runs
Every time any code touches the database, in both programs. init_db once at start-up.
What is inside
init_db
Builds the engine (a pool of connections to the database named in DATABASE_URL) and creates any missing tables.
session_scope
A with block that gives you a database session, commits if the block finishes and rolls back if it raises. Everything inside is one transaction.
is_postgres, is_initialized
Small checks (for example, to know whether row locks are available).
How it is used
Imported by essentially every file here. It does not run a database; the database is PostgreSQL in Docker, and this file only connects to it.
Stack
SQLAlchemy (engine, connection pool, sessionmaker), the psycopg driver for PostgreSQL, contextlib.contextmanager, with a SQLite file fallback for tests and quick demos.
Why it helps the app
One safe way to read and write: an error part-way never leaves half-saved data, and many calls can use the database at the same time through the pool.

YOU ASKED ABOUT THISHow the tools are exposed to the model

A "tool" is a Python function the model is allowed to ask for (log a meal, book a call-back). The model cannot run code. It can only write a request, and our code decides whether to run it. Here is the whole path for book_callback.

    The prompt line the model reads

    - book_callback(in_minutes: int?, at: str?, reason: str?): Book a call back to THIS parent about the reminder in progress,
  in N minutes or at a parent-local time (e.g. '16:15'). Booking again during the same call moves the existing booking.

    That line is generated, not typed by hand: db_tools.tools_text(CONVERSE_TOOLS) reads each tool's name, argument types and description from the registry, so adding a tool to the registry and to the allow-list is enough for the model to know about it.

    What the model writes, and what comes back

    model  ->  {"say": null, "actions": [{"tool": "book_callback", "args": {"in_minutes": 2}}], "end_call": false}
code   ->  TOOL RESULTS: [{"tool": "book_callback", "ok": true, "at_local": "11:25", "spoken": "eleven twenty-five", "call_id": 20}]
model  ->  {"say": "All right, I will call you again at eleven twenty-five.", "actions": [], "end_call": true}
    Why not the model provider's built-in tool calling? The registry can also produce that format (openai_tool_specs), but the live agent does not use it. It uses plain text descriptions and a JSON reply instead, so one format works for the spoken words, the actions and the end of the call, and it works with any model. The price: the model can write an action that is wrong, so every request passes through call_tool, which checks the tool name, scope, argument names and types, refuses a parent_id argument (the call supplies it), turns every error into {ok:false}, and writes an audit event.
    Two safety layers on top. run_tools only accepts names in CONVERSE_TOOLS (9 tools), so admin tools like update_meal_time are unreachable even if the model names them. And the logging tools check that the quoted words really appear in what the parent said.
