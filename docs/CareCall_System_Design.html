CareCall system design

CareCall phones an elderly parent on a schedule to remind them about medicines and appointments, asks what they ate and records it, books a call-back or a new reminder when they ask, and tells their adult child what happened. This page describes how the system is built today, as of 20 October 2026.

Who uses it

A caregiver (an adult child) signs up, adds a parent, and watches a dashboard. The parent only ever uses a phone call.

What the agent does

Exactly three things: remind, log diet, and schedule call-backs or reminders. Everything else is declined, except emergencies, medical questions, loneliness and scams, which go to the caregiver.

Design rule

Guarantees live in code, judgment lives in the model. The model chooses words and tools. Code enforces quiet hours, attempt caps, evidence quotes, the emergency check and what may be booked.

BIG PICTURESystem architecture

Three programs run on one host: the web server, the scheduler and (in development) an ngrok tunnel. They share one PostgreSQL database. Twilio reaches the server only through the public tunnel address, because Twilio calls us for every event in a call.

HTTPS request/responseWebSocket (long-lived, two-way)HTTP streaming (SSE)SQL

Why the public address exists

An LLM API is something we call. Twilio is also something that calls us: when the parent answers, for each thing they say (trial mode) or each 20 ms of audio (stream mode), and when the call ends. Our laptop has no address on the internet, so ngrok keeps an outbound connection to its servers and forwards requests arriving at the public address down it. In production the server would sit on a cloud host with its own HTTPS address and the tunnel would disappear.

POSTGRESQLData model

Timestamps are UTC; local time is derived from the parent's time zone at the edges. Every fact the agent records carries the parent's exact words. events is append-only and acts as the audit trail.

Identity

accounts (email, scrypt hash, caregiver), auth_sessions (SHA-256 of cookie token, expiry), caregivers (name, phone, alert mode), parents (name, preferred name, phone, language, time zone, consent time, calling on/off), parent_caregiver (who looks after whom).

Plan

meal_profile (meal, time, source: only caregiver-set times move the schedule), medicines (name, dose, before/after/with food, meal anchor, offset), reminders (message, due time), routines (key, type, config).

Calls

call_attempts (status, kind, attempt number, scheduled time, idempotency key, occurrence key, Twilio sid, outcome), transcript_turns, call_summaries, callbacks (a promise made on a call).

Facts

meal_logs, medicine_logs, reminder_acks (each with the source utterance and a confidence), alerts (emergency, warning, info), notifications (what was sent to a caregiver).

Audit

events (call, type, JSON payload, time) is written by almost every step. test_notes holds the LLM-written notes on test runs.

STATE MACHINELife of one call

A call attempt is in exactly one state. Only the legal moves below are allowed; an illegal or repeated move (for example a duplicate Twilio "completed" webhook) is recorded as state.ignored and does nothing. That makes status handling safe to repeat.

FromToCaused by
scheduleddialingDispatcher claims it, commits, then asks Twilio to ring
scheduledcancelledCaregiver pauses calls, parent opted out, or the next occurrence made it pointless
scheduledin_progressA text-channel session (tests) opens it directly
dialingringing, no_answer, failedTwilio status webhooks, a dial error, or the reaper after 180 s of silence
ringingin_progress, no_answer, failedAnswered, unanswered or busy, or failed
in_progresscompletedThe agent finished the conversation
in_progressabandonedThe line closed before the agent finished (hang-up, drop)
in_progressfailedStuck for 25 minutes (a lost webhook), set by the reaper

Idempotency keys (duplicate calls cannot happen)

Two levels, both computed, never random:

occurrence key   2:tablet_3_reminder:2026-10-20:s1       one planned event: parent, routine, parent-local date
attempt key      ...:s1:a1    the first try
                 ...:s1:a2    the retry that follows attempt 1 (no answer, cut off, technical failure)
                 ...:s1:cb2   the call the parent asked for, as attempt number 2

The attempt number only goes up, so "the call that follows attempt N" always has the same key. If post-call processing runs twice, or a call-back is booked live and then confirmed after the call, the second insert hits the unique constraint and returns the first row. That is why the log showed followup.already_scheduled after the booked call-back on real calls.

PLANNER · DISPATCHER · REAPER · OUTCOMEScheduling engine

The database is the queue. A call is a call_attempts row with status scheduled and a time. Nothing is held in memory, so a restart loses nothing and several workers could share the work.

  1. Planner (hourly, and at onboarding)For each parent with calling on, computes today's local fire time for every routine from the meal profile, converts to UTC and inserts one scheduled attempt per routine per day. A moment more than 10 minutes in the past is skipped ("do not call at 4 pm about a 1 pm lunch"). Running it twice creates nothing new.
  2. Dispatcher (every 10 s)Selects due rows with FOR UPDATE SKIP LOCKED. Per row: parent paused means cancel; parent already on a call means postpone 5 minutes; otherwise set status dialing and commit first, then ask Twilio to ring. A dial error becomes a failure and goes to the outcome engine.
  3. Reaper (every tick)Calls stuck in dialing or ringing for 180 s, or in progress for 25 minutes, are marked failed so a lost webhook can never lock a parent out.
  4. Outcome engine (after every call)Rules plus an LLM judge decide what the call was: completed, call-back requested, cut off, no answer, opted out, technical failure. It then creates the next attempt: an immediate retry when cut off mid-sentence, a retry after 10 minutes when unanswered, 5 minutes after a technical failure, or the exact call-back the parent asked for. At most 2 attempts per reminder, and a retry that would land after the next planned call is dropped.
  5. Live booking during the callWhen the agent books a call-back it writes the attempt immediately, so the dashboard shows it before the call ends. The outcome engine later finds it already there.

Rules that shape the calendar

  • Quiet hours 21:30 to 07:00 in the parent's time zone: call-backs and retries are moved to the morning, and a request that would fall inside is explained to the agent with a reason code.
  • Next reminder first: a call-back may not be later than 10 minutes before the parent's next planned call.
  • Attempt cap: the first call plus one more, then move on. A call-back chain stops at attempt 4.
  • Meal times: only times set by the caregiver move the schedule. A parent can ask to be reminded again or about something else, never to move a meal.
  • Dispatch granularity: because the loop wakes every 10 s, a call dials up to 10 s after its time (observed: 2 to 8 s).

LANGGRAPH + LLMConversation engine

The model holds the conversation. It sees the whole history and replies with one JSON object each time, never free text:

{ "say": "All right, I will call you again at 11:25." | null,
  "actions": [ { "tool": "book_callback", "args": { "in_minutes": 2 } } ],
  "end_call": false }

The graph, one run per parent sentence

  • open: the first turn. Builds the facts for the call and speaks a scripted opening (no LLM), so the first words are instant.
  • safety: an emergency pattern check on the parent's words, and a count of silent turns. This is ordinary code, not the model.
  • escalate: emergency path. Raises the emergency alert, tells the parent help is being informed, ends the call.
  • give_up: three silences in a row. Records "not acknowledged", "medicine unclear" or "meal unclear" as appropriate, raises a warning, ends the call.
  • agent: one LLM call (JSON mode, thinking disabled). Holds back commitments if the draft ends with a question.
  • tools: runs the requested tools through the registry, then loops back to agent if a result matters or something failed, up to 4 steps.
  • finish: caps length at 60 words, blocks leaks, applies the repeated-line guard, builds the reply and the end reason.

Memory

The conversation is a list of plain messages kept per call by LangGraph's in-memory checkpointer under thread_id = call-<id>. Each parent sentence is appended as a user message, each model reply as an assistant message holding the JSON it produced, and each tool result as a user message beginning TOOL RESULTS:. The last 40 messages are sent. A ring-back adds the previous attempt's transcript to the system prompt. Because memory is in the process, a server restart mid-call loses that conversation.

The registry also holds tools the live agent cannot reach: pause_calls and finish_occurrence (system scope), update_meal_time and resume_calls (admin scope), and several scheduling helpers used after a call. Every call goes through one checker: unknown tool, wrong scope, a forbidden parent_id argument, wrong argument types, and any exception are turned into {ok:false, ...} and an audit event. A refused booking returns a reason code and alternatives, and the model is told never to book a different time than the one the parent agreed to.

Guards that do not rely on the prompt

  • Ask before promising: if the draft say ends with a question and the same reply requests book_callback or add_reminder, those actions are dropped that turn and the parent's answer decides. Logging and alerts are not held.
  • Evidence: a logged fact needs a quote that appears in what the parent actually said.
  • Emergency pre-check before the model sees the sentence, and a loop guard: the same line a third time ends the call. At most 24 parent turns.
  • Length and leaks: replies over 60 words are cut; anything that looks like an instruction, an e-mail or a phone number is replaced.
  • Fillers: while a slower tool runs the agent says something like "Umm... hold on a moment" in stream mode, so the line is never dead. In trial mode this does not work and is currently only noise.

Scope

The prompt gives the agent three jobs and a strict list of what to decline with one sentence and a return to the job. Four things are never declined and go to the family: emergencies, medical questions ("that is a question for your doctor or pharmacist" plus a warning), loneliness, and scams such as OTP or bank requests. For a one-off reminder, a request to change it gets: "I cannot change a fixed appointment, but I can remind you again at a time of your choice", then a booking for the time they name.

After the call

Post-call processing writes a summary and flags anomalies (a message for the caregiver, an unclear answer), notifies the caregiver, and hands the call to the outcome engine, whose LLM judge decides the next step. Models in use: GPT-6 Luna for the live agent and the judge, chosen over a cheaper Qwen model after comparison (114 vs about 112 of 116 tool-selection runs, and no missed medical alerts on the guardrail set, at about 0.3 to 0.6 s more per turn and roughly three times the cost).

TWO PHONE MODESVoice paths

TWILIO_VOICE_MODE picks how the call's audio is handled. The agent, tools, scheduling and database behave the same in both; only listening and speaking change.

HTTPSWebSocketSSESQLLLM

Trial mode (gather): Twilio listens and speaks

Works on a trial account. Twilio's own recogniser (set to English-India) turns speech into text and posts it to us; we answer with text for Twilio's own voice (Polly "Aditi"). Gnani is not used. There is no streaming: the LLM reply is complete before anything is sent, and each turn is one HTTP round trip.

    Stream mode (stream): Twilio carries audio, Gnani listens and speaks

    Needs a paid Twilio account, because the trial blocks the <Stream> instruction. Twilio is only the phone line: it streams the parent's voice to our server over a WebSocket and plays back the audio we send. Gnani does the recognition and the voice. The LLM text is still not streamed; the voice audio is.

      Streaming speech details

      • Text-to-speech: Gnani's SSE endpoint sends base64 PCM chunks. The adapter re-cuts them into exact 320-byte (20 ms) frames, because a padded short frame at every chunk boundary would sound like stutter. First audio arrives about 0.19 s after the request instead of 0.71 s for a whole clip. If the stream fails before any audio it falls back to the whole-clip call.
      • Speech-to-text: frames must be exactly 1024 bytes. Gnani sends only "speech started" and one final transcript per segment, never partial text.
      • Barge-in and silence: "speech started" while the agent is playing makes the bridge send Twilio a clear to flush playback. It also cancels the "are you still there?" timer (7 s after the agent finishes). Twilio echoes a mark when playback reaches it, which tells the bridge the agent has stopped talking.
      • Fillers across threads: the tool runs in a worker thread, the audio is sent by the event loop. A bridge function uses run_coroutine_threadsafe to play the filler immediately and in order.

      Trial-mode details

      • The voice instruction arrives from Twilio without a signature header on trial accounts. It is accepted on a per-call HMAC token carried in the URL, only when the header is absent; a present but wrong signature is refused. Status webhooks do arrive signed.
      • If the agent takes more than 3 s, Twilio is told "One moment", then pauses and returns to a /twilio/wait address for the answer, repeating up to 6 times. This avoids one long request.
      • Conversation sessions live in server memory, so a restart mid-call ends that call with an apology.

      Dashboard

      A static page that polls /api/dashboard every 2 seconds and ticks countdowns locally against the server clock. It shows the next call, a calendar of waiting and live calls (a newly booked call-back flashes in), the live transcript, what the agent recorded with the parent's quotes, routines with their next call, recent calls, and an activity log of every event. All data from the database or the parent is escaped before it is inserted into the page, because transcripts come from speech recognition.

      CONCURRENCY · FAILUREReliability and concurrency

      Many calls at once

      The server is asynchronous: one event loop handles all WebSockets and webhooks, so thousands of idle connections cost almost nothing. The model call, database writes and each LangGraph run are blocking, so they run in worker threads and never freeze the loop. Each call has its own session and thread id, so calls cannot see each other's memory. Postgres has a connection pool (10 plus overflow), and every unit of work is one transaction.

      Failure cases and what happens

      FailureHandling
      Twilio refuses to ringDial error: call marked failed, outcome engine schedules a retry in 5 minutes.
      Webhook lost or call never reports backReaper fails it after 180 s (dialing) or 25 min (in progress), then retry logic.
      Parent hangs up mid-sentenceMarked abandoned; the LLM judge sees the transcript and usually books an immediate retry.
      Parent on another callDispatcher postpones 5 minutes.
      Server restartsScheduled calls are safe in the database. A call in progress loses its in-memory conversation and is closed.
      Model slow or errorsPhone mode says "One moment" and retries; an errored step produces "Sorry, could you say that again?"; after the step limit the parent is told someone will follow up.
      Two workers pick one callSKIP LOCKED plus commit-before-dial: the second worker never sees it.
      Same request twiceComputed idempotency keys, with the insert in a savepoint so a lost race is a no-op rather than a crash.
      Database not runningThe server hangs at start-up waiting for the connection. Docker must be up first.

      HOW IT IS CHECKEDTesting and evals

      247 automated tests

      Run on SQLite by default and on real Postgres for concurrency. A scripted model checks the plumbing and guarantees: memory, the tool loop, refusals, emergencies, silence, idempotency, state machine, the Twilio protocol with a simulated Twilio, accounts, onboarding, phone-mode turns.

      Tool-selection test

      carecall tool-use: 60 cases against a real model, covering meals, medicine, reminders, scope, scams, emergencies, injection and conveying reminders. Each run is judged on tools called and refused, and on what was said.

      Persona simulations

      An LLM plays a parent from a backstory against the live agent; a judge with database facts grades it; an LLM writes notes. Traces appear in Langfuse as eval:<scenario>.

      Live audio test

      carecall stream-test plays Twilio against the running server with real Gnani speech both ways, a throwaway parent with a dead number, and cleans up any call-back it booked. It found the barge-in bug.

      Known test-environment quirk: test_gnani_route fails while the real server is running on port 8000, because it checks that the server is not reachable.

      RUNBOOKRunning it

      1. Start Docker Desktop, then the databases: docker compose up -d in docker/app (Postgres) and docker/langfuse (tracing). Give Langfuse a minute before starting the app.
      2. carecall tunnel: opens ngrok and writes PUBLIC_BASE_URL into .env. Keep it running; the address changes if it restarts.
      3. carecall serve, wait until /health answers, then carecall scheduler. Starting both together on a brand-new database can fail on creating the same table.
      4. Open /dashboard, create an account, add a parent.
      5. Every command must run from the project folder with its virtual environment, or Python will not find the carecall package.

      For a real deployment: a managed Postgres, a cloud host with its own HTTPS address (WebSocket-capable, not a short-lived serverless runtime), secrets in the host's environment, the server and scheduler as separate always-on processes, and a paid Twilio account.

      NEXTLimits and roadmap

      Known gaps

      • Languages: everything is English-India. Tamil and Hindi need per-parent language through speech-to-text, the voice, the prompt, the scripted lines and the emergency and scope checks.
      • Twilio account: the live Gnani pipeline needs a paid account. Until then the trial mode is used and its recogniser misheard words in real calls.
      • Database: no migrations (create_all never changes an existing table, and starting two processes at once on a new schema can race), no backups, no retention policy for transcripts and events.
      • Trial-mode quality: the stall phrase is spoken after the work, not during it, and each line is a separate spoken piece, which adds gaps.
      • Garbled audio: a misheard sentence is answered with the out-of-scope refusal instead of "sorry, I did not catch that". Twilio supplies a confidence score that is not used yet.
      • Auth hardening: no email verification, password reset or rate limiting.
      • Tracing start-up: if Langfuse is down when a process starts, tracing stays off for that process until it restarts.
      • Memory: an in-progress call does not survive a restart.
      • Docs: the earlier books and the call walkthrough page describe the behaviour before several of these changes.

      Suggested order

      1. Upgrade Twilio and run the stream mode on a real phone.
      2. Language support, starting with Tamil, using Gnani for recognition and voice.
      3. Alembic migrations, backups and a retention rule.
      4. Confidence handling for misheard speech; drop the stall phrase in trial mode.
      5. Cloud deployment with a managed database and secrets management.
      6. Auth hardening and a push-based dashboard.
